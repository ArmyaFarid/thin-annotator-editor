Two Ways to Draw a Border

The outline around an annotated mineral grain used to be burned into a bitmap, pixel by pixel, at the resolution of the image. Now it is a stroked path, re-drawn every frame at the resolution of the screen. Here is what each approach does, put side by side.

Where the border comes from

One walks the pixel grid looking for edges. The other computes the edge once and describes it.

A kernel over every pixel

Composite all layers into a full-image canvas, read it back with getImageData, then test every pixel against its neighbourhood: 

// only a mask pixel can ever become border
if (!occupied(x, y)) continue;

let isBorder = false;
outer: for (let dx = -bt; dx <= bt; dx++) {
  for (let dy = -bt; dy <= bt; dy++) {
    if (!occupied(x + dx, y + dy)) {
      isBorder = true; break outer;
    }
  }
}

The result is written into a second full-image canvas and blitted through the view transform with imageSmoothingEnabled = false.

A path, traced once

Composite the layers into a bounding-box-cropped binary grid, then follow the boundary between set and unset pixels, emitting a vertex only where it turns: 

const rings = traceCrackRings(occ, bw, bh);

// one Path2D for the whole mask,
// outer rings and holes alike
for (const ring of rings) {
  path.moveTo(ring[0].x, ring[0].y);
  for (let i = 1; i < ring.length; i++)
    path.lineTo(ring[i].x, ring[i].y);
  path.closePath();
}

The path is cached until the mask's content changes, then filled and stroked each repaint.

The unit — and why the old one could not work

This is the whole argument. Everything else follows from it.

Thickness in image pixels

theme.mask.borderThickness = 2 was a kernel radius on the image's pixel grid, not a stroke width. The theme file had to carry an explicit units exception because of it.

A thickness measured in image pixels is multiplied by the zoom before it reaches the screen. There is no value that is correct at two zoom levels at once — the number is not wrong, the unit is.

Thickness in screen pixels

The stroke divides by zoom at draw time, so it lands on screen at a fixed width no matter the magnification: 

ctx.lineWidth = (2 * theme.mask.strokeWidth) / zoom;

This is not a new idea in the codebase. Polygon.render has always done exactly this, which is why polygon outlines never had the problem. Masks now share the behaviour because they share the technique.

Which side of the boundary the ink lands on

An easy thing to get wrong, and the failure is silent: the mask simply reads as slightly bigger than it is.

Strictly inside, by construction

if (!occupied(x, y)) continue; means a pixel outside the mask is skipped before anything is written. Nothing was ever painted beyond the segmented pixels — the painted extent equalled the true extent, and the border ate inward into the fill.

Inside, but only because it is forced

A canvas stroke is centred on its path by default, which would have put half the width outside the mask for the first time — five image pixels of inflation at 0.25× zoom, enough to make neighbouring grains appear to overlap. So: 

ctx.clip(path, "nonzero");
ctx.lineWidth = (2 * width) / zoom;  // double
ctx.stroke(path);                    // inner half survives

Preserving the old behaviour here was a requirement, not a detail. In a tool where someone is deciding whether a mask covers a grain, a renderer that silently draws every object slightly too large is worse than one that draws an ugly border.

Does the outline sit where the mask sits?

The codebase already had a boundary tracer. It could not be reused for display, and the reason is worth seeing rather than reading.

Tracing pixel centres

Tracing the cracks between pixels

Half a pixel is invisible at fit-zoom and obvious at 8×, which is why the display path needed its own tracer. The original stays where it is, serving anchor-mode conversion. No simplification tolerance, no minimum feature size and no smoothing are applied anywhere in the display path — verified by rasterizing traced rings back and XOR-ing against the source grid across edge cases, fuzz grids and real RLE masks. How the holes get cut

A grain with a pore, or a region subtracted by hand, needs the middle removed.

Compositing operations

Fill layers drawn with source-over, hole layers with destination-out, onto a full-image scratch canvas. Each RLE layer first becomes its own white-on-transparent alpha canvas.

Correct, but it means the hole is only ever expressed as pixels that were erased — there is no object representing the hole.

Winding direction

The tracer returns outer rings and hole rings in one pass, wound in opposite directions. Filling everything with the nonzero rule cuts the holes out automatically — no classification step, and it nests to any depth.

Nonzero rather than even-odd matters for one case: two overlapping fill layers must union, and even-odd would punch a hole where they overlap.

A quiet improvement: because the grid is composited before tracing, awkward topology now resolves correctly — a hole layer straddling the fill edge, or two fill layers touching at a single corner. By trace time it is just a set of pixels.

What to carry away

What got better

  • Constant border thickness at every zoom, identical to polygon outlines.
  • The 300M-operation border pass is gone; editing got faster, not slower.
  • Gigabytes of canvas became kilobytes of geometry.
  • Small grains keep their fill instead of rendering as solid blobs.
  • Antialiased edges, so sub-pixel features render faint but present instead of shimmering.
  • The theme lost its one units exception — every constant is CSS pixels now.

What to watch

  • The pixel staircase is now visible at high zoom. That is what the mask genuinely is; the old band was wider than the steps and hid them. The app already draws the real pixel lattice above 12×, so the outline now agrees with a grid the annotator can see.
  • Panning repaints every mask, so per-frame cost moved from blitting to stroking.
  • Corner-touching pixels now count as connected — a genuinely new decision, applied consistently.
  • Hover became a brighter stroke rather than an additive glow.

Nothing here touches what gets saved. mergeToCanvas flattens layers to RLE through its own code path and never calls into rendering, so there is no format change and existing tasks load unchanged. Contours are a display concern only — any downstream measurement still comes from the stored mask.
